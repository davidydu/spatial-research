## Purpose and evidence boundary

Use the same small programs to compare Python designs before implementation. The facts below were checked against original Spatial source at the pinned revision in [[reference-clones]]. Expected outputs are derived from the source and small arithmetic; they are not results from a new Python compiler or a fresh Scala execution.

The first [[2026-09-30-pure-python-programming-model|tiled-scale Python sketch]] is a proposal. No candidate Python form has passed an implementation test. The three cases are discriminating examples, not a complete language-support inventory.

## E1 — Tiled scale

Source: `spatial@e7a8f2f:test/spatial/tests/ee109/Lab1Part2DramSramExample.scala:6-43`.

The source uses 32 input elements, tile size 16, distinct input/output SRAM buffers, sequential traversal of tiles, a loop multiplying each loaded element by the scalar argument, and an output transfer. The host constructs a reference by multiplying each input element by the same scalar.

For inputs `0, 1, …, 31` and scale `3`, the expected output is `0, 3, …, 93`. Preserve both buffers and the load/compute/store structure in both initial Python alternatives; changing the algorithm would undermine the comparison.

Questions exposed: port declarations, local allocation, memory views, transfer direction, loop regions, and host versus kernel execution. Later variants may change a legal tile size or compose another supported operation. Do not silently add a tail policy to the original divisible-size example.

## E2 — Scalar reduction

Source: `spatial@e7a8f2f:test/spatial/tests/feature/control/ReduceTiny.scala:7-15`.

The source allocates a `1 × 16` SRAM, initializes each element to its index, reduces its values with identity `0` and addition, and writes a scalar output. The expected result for this case is `120`.

Questions exposed: initialization before reads, contribution and combination expressions, identity, and result lifetime. This small sum does not distinguish every reduction tree from an ordered fold. Add a case that makes the chosen numeric/reassociation policy observable when that policy is proposed.

The neighboring `ReduceAccumTiny` example provides explicit-register and parallel-lane variants: `spatial@e7a8f2f:test/spatial/tests/feature/control/ReduceTiny.scala:27-37`. Keep these as named extensions, not unannounced replacements for E2.

## E3 — Runtime branch with FIFO state

Source: `spatial@e7a8f2f:test/spatial/tests/feature/control/FIFOBranch.scala:9-31`.

The source allocates two FIFOs of capacity 128, fills them from runtime counts, then chooses which FIFO to dequeue based on whether the first is empty. The selected value contributes to a reduction. Its reference sums the values generated by both counts.

For counts `13` and `25`, the source-derived expected result is `78 + 300 = 378`. Both candidate Python forms must represent the condition and both possible dequeue operations without executing a sample-dependent branch during capture.

The final sum alone is weak evidence: several wrong consumption orders could produce 378. Record which queue each selected operation consumes and its resulting state under the candidate's explicit execution model. Do not infer a universal cycle order or back-pressure model from this source listing alone. FIFO capacity/error behavior and permitted reduction effects remain [[02 - Python Open Questions|open semantic questions]].

## Planned variants and diagnostics

For each candidate, explain the intended outcome for an uninitialized read, incompatible numeric use, and unsupported syntax. Add a branch-sensitive case where a misplaced FIFO read changes the result or state. Mark each as a proposed acceptance/rejection policy until a semantic decision adopts it; earlier Rust diagnostics are useful examples, not automatic Python requirements.

Record forms in [[PY-R001 - Programming Model Study]] and link back here rather than duplicating their source contracts. Future executable fixtures must name the adopted decision/specification and keep expected results separate from observed results.
