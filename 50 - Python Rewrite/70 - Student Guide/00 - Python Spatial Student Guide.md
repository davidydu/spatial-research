# Python Spatial student guide

Write an accelerator in Python Spatial, test its generated C++ on your computer, then check the generated hardware through HLS and RTL simulation.

> [!important] Documentation preview
> The compiler supports a growing subset of the language. Native C++ execution and generated HLS testbenches exist in developer tools. The simple student launcher, test fixtures and case-export interface described here are planned, not released. Check [[80 - Initial Compiler Goal|current implementation progress]] before choosing project features. The detailed [support ledger](https://github.com/davidydu/spatial-py/blob/work/initial-reference/docs/support-ledger.md) requires access to the private compiler repository.

## Two kinds of Python code

| Code you write | What happens to it |
|---|---|
| Accelerator source | Our Python compiler reads and checks it, then generates C++ for the supported target. |
| Test and host code | Ordinary Python prepares inputs, calls the compiled accelerator, calculates expected answers and checks results. |

Your test code can use ordinary functions, loops, files and testing libraries. It does not need to fit the accelerator language subset. A reference calculation in a test stays on the CPU and is not synthesized.

The normal student execution path will run generated C++. Our separate Python reference interpreter helps compiler developers verify language behavior; students will not need to run it to pass a functional test.

## What a passing test means

| Stage | What executes | What a passing test establishes |
|---|---|---|
| Native software test | Generated C++ on your CPU | The tested inputs produce the expected outputs or expected language faults. No HLS installation is required for the current native profile. |
| Vitis C simulation | The generated kernel and its wrapper in the vendor toolchain | The selected HLS project passes its functional testbench. |
| RTL co-simulation | Hardware generated by HLS in a simulator | The generated RTL passes the selected transactions and output checks. |
| FPGA test | A design loaded onto a physical board | The tested board application works with its actual interfaces. This is not implemented in the current Python project. |

Software test runtime is not hardware latency. A request such as `par=4` does not make a native test a measurement of four hardware lanes. [[2026-10-21-vitis-rtl-checkpoint|The existing hardware checkpoint]] records the limited programs already tested through RTL; newer local features have separate evidence.

**Current backend update:** [[2026-10-22-scalar-interface-checkpoint|The experimental HLS wrapper]] now takes explicit scalar seeds and returns separate values and initialization flags. Student source syntax and the intended C++ testing workflow are unchanged. Local tests pass; this changed wrapper still needs fresh vendor/RTL validation.

## How this guide will grow

Maintain the student guide here in the shared research vault as the language develops. For each user-visible language or testing feature, update its syntax, meaning, example, functional test and support status in the same checkpoint. As public interfaces become available, replace the marked sketches with examples exercised against the supported release. Keep the advanced testing route visible from the beginner tutorial so projects can grow beyond supplied lab cases.

Later, prepare a separate student-facing documentation publication containing the language guide, tutorials, API reference and testing instructions. Research deliberations, implementation handoffs and historical plans stay in the research collection. Until that separation, keep one editable copy of the guide in this vault; a second documentation repository or site is not needed yet. The existing research site already publishes this preview, so keeping it in the vault does not make it private. The later student release will present only the curated documentation and will need its own navigation and link checks.

This guide owns student workflows and examples. [[10 - Python Language Contract|Language contracts]] describe meaning, the support ledger records implemented behavior, and [[00 - Python Rewrite Index|research notes]] explain design choices. Link those records instead of maintaining a second language specification here.

The intended public testing surface includes compilation and execution, typed inputs, complete results, source diagnostics, custom checks, and export of concrete test cases. Exact API names and packaging are still open. The examples do not introduce a second testing language or require a particular test framework in the compiler core.
