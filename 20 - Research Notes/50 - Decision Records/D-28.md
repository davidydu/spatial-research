## Recommendation

Build a **Python Spatial language frontend, Python semantic compiler, and Python reference simulator**, using custom Spatial dialects on **xDSL**, followed by a checked implementation plan and an **HLS C++ backend**. Captured source is the primary kernel surface. A Python builder serves generators and tooling through the same unchecked model and checker.

This is the recommended architecture under the accepted pure Python direction. It is a concrete engineering choice with stated reversal conditions, not a proof that one architecture is optimal for every future workload.

## Why this choice

Source capture and a builder were compared on the same tiled-memory, scalar-reduction, and guarded-FIFO cases, followed by helper composition and matched diagnostic cases. R001/R004 support source-first as the primary writing interface; they do not establish measured user preference. Raw-source acquisition is a separate design choice from source capture: a callable frontend can also retain the function body. Its strongest cost here is a less familiar source-as-data workflow.

R006 compared custom Python IR, xDSL, and native MLIR Python bindings. xDSL fits nested typed regions, SSA values, and staged lowering while remaining inspectable Python. A bounded framework probe reproduced the need for a Spatial verifier: structural verification accepted a use before definition. The recommendation therefore includes private checked snapshots, explicit dominance/effect checks, and pass invariants. These mechanisms require implementation tests; the probe is not a Spatial compiler benchmark.

R003/R008 show why an ordinary arithmetic AST interpreter is insufficient for the full rewrite. State lifetime, aliases, consuming operations, bounded channels, termination, and external effects need represented rules. R009–R011 define the HLS responsibilities and capability gates before vendor scheduling. Source-only research does not establish hardware progress, numerical agreement, resource fit, or timing closure.

## Deliberate changes and boundaries

The proposed Python contract resolves original simulator/backend disagreements explicitly: exact typed arithmetic and rounding; ordered folds distinct from lawful/fixed-tree reductions; active bounds/initialization faults; bounded queues; dynamic vector checks; explicit state lifetime, merge/lock/window protocols, field-stream versus record-token behavior, and stop/cancellation admission. These are reviewable changes, not claims that every legacy backend already agreed.

Ordinary host Python replaces staged Scala host collections/files and old packaging. No initial literal port of Chisel/Fringe, Plasticine/PIR, Tungsten, Rogue, or every board tree is proposed. Their language-facing obligations remain in the coverage ledger, with target adapters or explicit exclusions. No arbitrary-Python-to-hardware promise, whole-application recognizer shortcut, or hidden native semantic authority is included.

## Strongest objections and reversal conditions

| Objection | How the proposal addresses it; when to reconsider |
|---|---|
| Captured Python is not ordinary Python function execution | Teach host/capture/runtime stages plainly; support explicit generators and raw-cell/source provenance. Add a reviewed callable adapter if concrete workflows justify it |
| xDSL is mutable and generic passes can violate Spatial effects | Private snapshots, owned immutable payloads, Spatial verifier and pass wrappers. Switch to custom IR if representative graphs or attributed performance evidence show an unacceptable framework conflict |
| A strict semantic model may need expensive HLS adapters | Keep exact meaning independent of targets; define explicit approximation profiles and validated domain restrictions. Reconsider a target route if required semantics lack a legal or useful implementation |
| Exact Python simulation may be slow | Predeclare R007 workload/latency/memory targets, keep structured loops/helpers, and profile before changing representation. No Rust fallback follows automatically from a slow prototype |
| Advanced concurrency may have several outputs or fail to progress | Define allowed traces, ownership/arbitration, bounded capacity, environment/fairness, and cancellation. Use independent bounded exploration and hardware protocol tests; do not substitute one simulator schedule |
| Research breadth can hide missing details | The 106-row ledger, 18 family gates, proposed contracts, independent reviews, and R01–R12 completion audit identify coverage and remaining execution evidence separately |
