# D-26 — Host-Language Architecture (compiler core × student surface × Python integration)

## Question

Which language hosts the Spatial rewrite's compiler core, which surface do
students write, and how does Python integrate?

| | Surface: external DSL (X) | Surface: Python-embedded (E) | Surface: both (B) |
|---|---|---|---|
| **Core: Rust (R)** | R-X | R-E | R-B |
| **Core: Python (P)** | P-X | P-E | P-B |

Integration depth for R-* cells: I0 CLI only; I1 + Python testbenches over
JSON; I1′ CLI shipped as a wheel; I2 PyO3 bindings over `check`/`build`/`run`;
In notebook cell magic.

Embedding styles for E/B cells (evaluated, not pre-chosen): tracing/operator
overloading; builder/context-manager; AST transform; hybrids.

Source: `90 - Meta/2026-06-26-rust-first-spatial-dsl-overlay.md` (Non-Goals);
`90 - Meta/2026-07-07-fundamental-design-review.md` (Issue 2); Q-165 in
[[20 - Open Questions]].

## Pre-registration (committed before any research note exists)

### Hypotheses and measures

The professor's stated position is "Python is easy to teach and easy for
students to pick up" — a claim about the student surface (X vs E), not the
compiler core (R vs P). D-26 evaluates the surface axis on teachability and the
core axis on maintainability, cost, and simulator performance, and reports
them separately.

- **H1 — easy to pick up.** Measure: per Tier-0 lab, hardware concepts exposed
  vs. non-hardware host constructs a student must learn, tallied identically
  for Scala, the external DSL, and the Python hybrid (angle 2);
  install-to-first-`check` (angle 11, full plan).
- **H2 — easy to teach.** Measure: on the fixed mistake list, which surface
  catches each mistake earlier and which explains it better, from real tool
  output (angle 3); precedent teaching reports (angle 1); reader study (angle
  14) if run.
- **H3 — steelman (not the professor's words): Python is already the course's
  tooling language and TAs can fix a Python compiler.** Measure: scenario cost
  (angle 8) and what catches a maintainer's mistake (angle 7, full plan).
  Written to win in angle 13.

**1a — Python precedents.** [[D-26-01a-precedent-python-over-core]] separates actual compiler ownership from output language: Exo and PyMTL have substantial Python compiler implementations, Allo owns Python frontend work over native MLIR, and calyx-py constructs textual hardware IR for Rust Calyx. Source locations and precise error formatting exist in Python precedents. Neither generated C nor a native simulator makes the compiler core itself Rust/C++. Teaching-use reports are evidence of use, not controlled proof of easier learning.

**1c — External syntax with Python tooling.** [[D-26-01c-precedent-external-dsl-over-core]] shows external-language checking in Dahlia, provenance in Calyx, binary wheel packaging through Ruff/maturin, and notebook hosting through cell magic. These mechanisms separate kernel syntax from installation and Python integration. They are precedents, not packages already shipped for Spatial.

**2 — Three fixed labs.** [[D-26-02-student-surface-comparison]] includes all three originals and all four alternative forms. The constructed union inventory counts 14/6/13/11/12 non-hardware concepts for Scala/external/tracing/builder/AST. It applies the same rubric to external `let`, `yield`, `using` and `:=`; it does not weight familiarity or measure learning time. The scalar “reduce” fixture actually contains nested Fold. GEMM ports retain product-by-product memory folding and explicitly disclose the missing `.buffer` counterpart and untested numerical/scheduling equivalence.

**3 — Actual diagnostic reachability.** [[D-26-03-error-paths]] records 24 external checks and 10 Exo cases/controls. All three canonical lab translations plus five variants hit current parser barriers; three legacy controls pass. Exo rejects an unbounded table read and accepts the bounded control while the current external checker accepts its unbounded LUT example and rejects the `requires` repair. Exo also accepts the uninitialized examples at its frontend. Scala evidence is source-only and Allo runtime is unavailable. These are mixed, partly analogous results; no honest overall error-parity percentage follows.

**5 — Boundary ownership.** [[D-26-05-boundary-design]] recommends unchecked surface AST ingress when an R-E/R-B design must share semantic diagnostics. Python owns Python syntax/subset errors; Rust can own shared names/constants/types/legality after ingress. Text ingress reuses parsing but requires precise source maps; checked IR ingress duplicates earlier semantic work or loses provenance. ADR 0002 specifies JSON host contracts, but the implemented new CLI currently exposes only text `check`.

**Mapping — Thirteen discriminating constructs.** [[00 - Python Mapping Overview]] reports tracing 6 yes/6 awkward/1 no, builder 13 yes, and AST 13 yes with all five information categories. These are first-rating designs, with explicit source/token retention and a DSL resolver; they do not constitute a working Python frontend or independent second-rating agreement. Native naming, host folding, branch capture, fixed-point ingress and FIFO evaluation order are concrete hazards. Q167 corrected one masked-tail statement; the independent audit also harmonized D0's rating basis.

**8 — Forward cost.** [[D-26-08-cost]] compares the same general controller-tree/interpreter milestone and credits specifications, oracles and recorded backend knowledge to every cell. The existing 5,363-line validator checks adapter forms; it is not a finished implementation of the general obligation calculus. Existing Rust work remains useful, but repository size is not a completion-time estimate. The week-3 message, new-lab construct and Vitis-bump scenarios identify owners and release work without invented person-weeks.

**10 — Synthesis.** [[D-26-10-recommendation-matrix]] separates the core and student-surface matrices, records integration availability, and evaluates each reversal individually. No personalized weighting is reported because both weight columns remain blank. Equal-weight and surface-only evidence identify no measured winner; a numerical total would require invented utilities and missing observations.

**13 — Strongest case for P-E.** [[D-26-13-case-for-p-e]] argues for a Python core and restricted AST surface when the enduring teaching staff maintain semantic code in Python and students already know Python. Its strongest advantage over R-E is staff ownership of semantic changes, not Python wrappers. These staffing and student conditions are explicit scenario assumptions. The case accepts real source/provenance/numeric work and leaves k=10 unmeasured.

## Recommendation

**Provisionally retain the Rust core and external reference surface for the next general-compiler milestone (R-X), with Python host tooling and packaging treated as independent deliverables. Keep a restricted, source-backed Python AST frontend as the leading surface alternative, without committing to two supported public surfaces yet. Reopen core ownership toward P-E if the enduring teaching team is demonstrably better able to maintain semantic code in Python and the same semantic, diagnostic and simulator gates can be met.**

This is an engineering judgment favoring continuity while decisive evidence is missing, not a measured winner under equal weights and not a claim that students should learn Rust. If David confirms the Python-maintainer premise as the governing priority now, P-E is a defensible decision from this evidence; the research does not establish a technical impossibility that overrides that priority. The professor's original teaching claim concerns the student surface and cannot itself decide the compiler-core language.

Even a single public E surface inherits these protocol requirements. No exception is silently granted here.

## Rejected alternatives and answers to the "case for" notes

“Rejected” below means not selected as the present recommendation, not disproved as an architecture.

1. **P-E: put semantic ownership with Python-oriented TAs.** Accepted as the strongest reason to choose P-E over R-E. A Python wrapper cannot make a Rust legality rule a Python-maintained rule. The missing fact is whether the actual long-term maintainers can and will own a Python compiler more effectively; scripting vendor tools is suggestive, not proof. A timed semantic repair/new-construct exercise would address that gap. Current continuity is provisional, and confirmed staffing priorities can change the decision. See [[D-26-13-case-for-p-e]] and [[D-26-08-cost]].
2. **P-E: Python compiler and diagnostic capability are real.** Agreed. Exo/PyMTL and the 13 AST mappings defeat any blanket “Python cannot preserve these semantics” argument. The open work is exact Spatial acceptance, numeric/effect behavior and origin retention, not proving that ASTs exist. The unchecked-AST boundary is a way to share these checks under R-E, not evidence that Python ownership is inferior. See [[D-26-01a-precedent-python-over-core]] and [[D-26-05-boundary-design]].
3. **P-E: familiar syntax can beat a lower raw concept count.** Agreed as a hypothesis. The external6/AST12 inventory cannot establish novice learning or repair success. Conversely, Python-looking scope/assignment with different semantics can mislead; a teaching comparison must include those cases. Current external parser failures are concrete counterevidence to any present diagnostic-superiority claim. See [[D-26-02-student-surface-comparison]] and [[D-26-03-error-paths]].
4. **P-E: the general Rust compiler is not already paid for.** Agreed. The cost note gives Python the same specification/oracle/backend knowledge and does not equate retained lines with avoided work. Retaining an existing implementation still offers an adaptation path; neither that advantage nor Python's maintenance advantage has been timed. No speed argument is credited without a matched interpreter benchmark. See [[D-26-08-cost]].
5. **R-B/P-B: preserve every option by shipping both.** Not selected without demonstrated two-surface demand. A common checker is valuable, but paired labs, origins, errors and release support remain recurring work. P-E's argument for one public surface is persuasive under its course scenario. See [[D-26-13-case-for-p-e]].
6. **R-E: Python students plus retained Rust assets.** This is the closest alternative if the student surface is chosen first. Its cost is frontend/provenance integration and the unchanged need for Rust semantic maintainers. I2 bindings are optional; packaging and JSON testbenches alone do not require an embedded frontend. Select it only with the registered E guarantees and evidence supporting its teaching benefit.
7. **P-X: Python core with external student syntax.** Entirely coherent if ownership and surface evidence point in different directions. It currently lacks a demonstrated advantage sufficient to justify changing the core solely to keep the same student surface; that is an unmeasured cost judgment, not rejection of Python parsing.

## Spillover (host-language-neutral findings about the DSL itself)

Route these to the syntax/teachability review; D-26 does not change them:

- The fixed mistake list calls direct DRAM writes invalid, but writable indexed DRAM is legal. Q166 stays open for a re-registered experiment; row 5 was not scored as a missed error.
- Canonical syntax and advertised diagnostic rules exceed the current parser/classifier. Keep valid control cases alongside negative cases so parser barriers are not mistaken for semantic checking.
- `let`, `yield`, `using`, `:=`, separate value blocks and const/runtime contexts have language-only teaching costs, even with an external DSL.
- Source-sensitive literal ingress and per-operator fixed-point normalization can differ from folding a host arithmetic expression first.
- Spatial target-index-before-RHS assignment differs from Python; immediate FIFO dequeue makes the difference visible.
- Declaration-ID order participates in the closed proof algorithm. It needs deterministic preservation and a teaching justification regardless of core language.
- A shape/legality message, source span, secondary label, suppression rule and ordering together form diagnostic parity; matching just text is insufficient.
- Fold versus reduce, initialized memfold, active temporary slices, tail masks and the missing `.buffer` counterpart require care when claiming equivalent lab ports.
