# HLSGen Backend Hook Survey

This survey looks for the least invasive Stage 0 path to generate HLS C++ for `Lab1Part1RegExample`. The target is intentionally narrow: one scalar `Accel`, two scalar `ArgIn`s, one scalar `ArgOut`, one `FixAdd`, and a normal C++ oracle returning success for inputs `3`, `5`, and output `8`.

## Current backend flow

The HLS mapping notes define Stage 0 as the scalar `Lab1Part1RegExample` path: `ArgIn`, `ArgOut`, `setArg`, `getArg`, `Accel`, `RegRead`, `RegWrite`, and integer add are the first artifact boundary (`/Users/david/Documents/Spatial Research/30 - HLS Mapping/60 - EE109 HLS Lowering Map.md:21-27`). The same map says the next build cut should identify the staged `AccelScope`, extract the two `ArgInNew`s, one `ArgOutNew`, two `SetReg`s, one `GetReg`, and the kernel-body `RegRead`/`FixAdd`/`RegWrite` pattern, then emit the tracer-bullet C++ shape (`/Users/david/Documents/Spatial Research/30 - HLS Mapping/60 - EE109 HLS Lowering Map.md:83-89`).

The tracer bullet pins the exact Stage 0 IR shape and output contract. It requires two `ArgInNew(Const(0))` nodes, host `SetReg`s, one `ArgOutNew(Const(0))`, one `AccelScope`, two kernel `RegRead`s, one `FixAdd`, one `RegWrite`, one host `GetReg`, and host-side print/compare/assert outside the kernel (`/Users/david/Documents/Spatial Research/30 - HLS Mapping/70 - Lab1Part1 Tracer Bullet.md:35-51`). The target HLS C++ is a single `extern "C"` function with `s_axilite` pragmas and `*argRegOut = argRegIn0 + argRegIn1` (`/Users/david/Documents/Spatial Research/30 - HLS Mapping/70 - Lab1Part1 Tracer Bullet.md:85-99`). The first done criteria are compiler identification, generated HLS C++, normal C++ compile-and-run, and explicit rejection of unsupported shapes (`/Users/david/Documents/Spatial Research/30 - HLS Mapping/70 - Lab1Part1 Tracer Bullet.md:133-141`).

Spatial stages an app by creating `InputArguments()` and calling `main(args)` inside `stageBlock` (`/Users/david/Documents/David_code/spatial/src/spatial/Spatial.scala:48-54`). `Spatial.runPasses` is the central manager: it creates analysis, transform, reporting, and codegen pass objects, then threads a block through them with the `==>` pass combinator (`/Users/david/Documents/David_code/spatial/src/spatial/Spatial.scala:60-164`, `/Users/david/Documents/David_code/spatial/argon/src/argon/Compiler.scala:203-224`). Codegen objects are allocated near the end of the pass setup: `ChiselGen`, `CppGen`, `RogueGen`, `TreeGen`, `HtmlIRGenSpatial`, `ScalaGenSpatial`, `PIRGenSpatial`, and `TungstenHostGenSpatial` (`/Users/david/Documents/David_code/spatial/src/spatial/Spatial.scala:146-159`).

The actual backend scheduling point is late in `Spatial.runPasses`, after final reporting and final IR printing. `treeCodegen` and `irCodegen` always run, dot backends are optional, Scala codegen runs under `enableSim`, Chisel runs under `enableSynth`, CppGen runs only when synthesis is enabled and `spatialConfig.target.host == "cpp"`, RogueGen runs when the target host is `"rogue"`, and PIR/Tungsten run under their own flags (`/Users/david/Documents/David_code/spatial/src/spatial/Spatial.scala:236-252`). CLI flags already follow this pattern: `--sim`, `--synth`, `--pir`, and `--tsth` mutate `SpatialConfig` backend booleans (`/Users/david/Documents/David_code/spatial/src/spatial/Spatial.scala:279-342`). The booleans live in `SpatialConfig` (`/Users/david/Documents/David_code/spatial/src/spatial/SpatialConfig.scala:21-28`, `/Users/david/Documents/David_code/spatial/src/spatial/SpatialConfig.scala:92-99`), and copied configs need explicit field propagation (`/Users/david/Documents/David_code/spatial/src/spatial/SpatialConfig.scala:102-139`).

Argon codegen is already pass-shaped. `Codegen` defines `lang`, `ext`, `out = config.genDir/lang`, and `entryFile`, clears generated files for that extension in `preprocess`, then emits `emitHeader`, `emitEntry`, and `emitFooter` inside `inGen(out, entryFile)` (`/Users/david/Documents/David_code/spatial/argon/src/argon/codegen/Codegen.scala:10-29`, `/Users/david/Documents/David_code/spatial/argon/src/argon/codegen/Codegen.scala:75-87`). Extra files can be emitted through `inGen(dir, filename)`, which uses `getOrCreateStream` and is gated by `config.enGen` (`/Users/david/Documents/David_code/spatial/argon/src/argon/static/Printing.scala:168-177`, `/Users/david/Documents/David_code/spatial/argon/src/argon/static/Printing.scala:213-224`). `FileDependencies` is optional packaging glue layered on top of `Codegen`: it accumulates `FileDep`/`DirDep` values and copies them in `postprocess` (`/Users/david/Documents/David_code/spatial/argon/src/argon/codegen/FileDependencies.scala:8-9`, `/Users/david/Documents/David_code/spatial/argon/src/argon/codegen/FileDependencies.scala:66-72`).

CppGen is not an HLS kernel backend. It is a C++ host-driver backend composed from `CppCodegen`, `CppFileGen`, `CppGenCommon`, `CppGenInterface`, `CppGenAccel`, `CppGenDebug`, `CppGenMath`, `CppGenArray`, and `CppGenFileIO` (`/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppGen.scala:5-13`). Its base declares `lang = "cpp"`, `ext = "cpp"`, and `entryFile = "TopHost.cpp"` (`/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppCodegen.scala:9-13`). `CppFileGen` opens `TopHost.cpp`, includes `FringeContext.h`, creates a `FringeContext("./verilog/accel.bit.bin")`, and calls `load()` inside `Application` (`/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppFileGen.scala:59-99`). `CppGenAccel` handles `AccelScope` by visiting the block inside `inAccel`, then emitting host-side register counts, cache flushes, `c1->run()`, timing, and instrumentation reads (`/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppGenAccel.scala:16-36`, `/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppGenAccel.scala:58-101`).

The Stage 0 node vocabulary exists in CppGen but points at the host ABI, not a kernel body. `ArgInNew`, `HostIONew`, and `ArgOutNew` populate mutable host ABI collections; `RegRead` emits a local value; `RegWrite` emits only a comment; `SetReg` and `GetReg` call `c1->setArg` and `c1->getArg`; `ArgAPI.hpp` is generated from the collected ABI order (`/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppGenInterface.scala:20-35`, `/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppGenInterface.scala:42-80`, `/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppGenInterface.scala:138-164`). `FixAdd` has the desired simple expression rule (`/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppGenMath.scala:26`), but CppGen suppresses generation while inside the accelerator because `AccelTraversal.inAccel` disables `config.enGen` for backends other than `"accel"` or `"tree"` (`/Users/david/Documents/David_code/spatial/src/spatial/traversal/AccelTraversal.scala:13-25`, `/Users/david/Documents/David_code/spatial/src/spatial/codegen/cppgen/CppFileGen.scala:7-10`). That suppression is correct for a host driver and wrong for an HLS kernel emitter unless the new emitter opts into accelerator-style generation.

The test harness can run custom backend objects without changing `Spatial.runPasses`. `DSLTest.Backend` models a compile/make/run backend with backend args and generated directories (`/Users/david/Documents/David_code/spatial/argon/src/argon/DSLTest.scala:88-131`). Its `compile` path calls `init`, sets `IR.config.genDir`, `IR.config.logDir`, and `IR.config.repDir`, then calls `compileProgram(args)` (`/Users/david/Documents/David_code/spatial/argon/src/argon/DSLTest.scala:133-151`). Its `runBackend` chain is compile, make, and run (`/Users/david/Documents/David_code/spatial/argon/src/argon/DSLTest.scala:240-253`). `SpatialTest` already contributes named backends such as Scala, VCS, Zynq, ZCU, AWS, CXP, ZCUSynth, VCSTest, and CS217 (`/Users/david/Documents/David_code/spatial/src/spatial/SpatialTest.scala:33-151`), while `PlasticineTest` shows a more custom backend style that overrides generated paths and runs a specialized flow (`/Users/david/Documents/David_code/spatial/src/spatial/PlasticineTest.scala:27-51`).

## Minimal hook options

|---|---|---|---|---|

It gives a normal `gen/hls` output root via `Codegen.lang` and a durable CLI surface. | It touches central manager code and config copy logic (`SpatialConfig.scala:102-139`). It also runs after the full Spatial transform pipeline, so Stage 0 must tolerate final IR shape rather than only the freshly staged shape. This is slightly larger than needed for the first Lab1 proof. |
| B | Standalone HLS codegen invoked manually in tests | Implement a new `HLSGen` pass or extractor, then call it from a Lab1Part1-specific test backend, `postprocess`, or `checkIR` path after `compileProgram` has produced the final block. The backend can compile and run the generated C++ oracle with a normal C++ compiler. | This is the least invasive Stage 0 hook. The manager still needs a small test entrypoint and a disciplined output path so generated artifacts are reproducible. Promotion to option A is a follow-on once the extractor is proven. |
| C | Piggyback on CppGen | Add HLS mode branches or mixins under `cppgen`, reusing type remap and math emission while overriding headers, `AccelScope`, `ArgOut`, `RegWrite`, dependencies, and footer. | It reuses the existing `FixAdd` expression and parts of the scalar type spelling (`CppGenMath.scala:26`, `CppGenCommon.scala:75-100`). | This is the least attractive path. ## Recommended Stage 0 integration path and why

Use option B for the first Stage 0 manager implementation: build a standalone `HLSGen`/extractor pass and invoke it from a Lab1Part1-specific test flow. Keep the new generator architecturally pass-shaped, but do not wire it into `Spatial.runPasses` until the scalar tracer bullet is generated and checked.

The smallest useful implementation is:

1. Add a new `spatial.codegen.hlsgen` generator with `lang = "hls"` and `ext = "cpp"` so output naturally lands under `gen/<test>/hls`. It should either avoid `AccelTraversal.inAccel` or set `backend = "accel"` before visiting an `AccelScope`, because `inAccel` disables `config.enGen` for ordinary host backends (`/Users/david/Documents/David_code/spatial/src/spatial/traversal/AccelTraversal.scala:13-25`).
2. Emit a single kernel source and a small host oracle source. For Stage 0, the extractor should accept only the tracer shape from the mapping notes: two `ArgInNew`s, one `ArgOutNew`, two host `SetReg`s, one `AccelScope`, two `RegRead`s, one `FixAdd`, one `RegWrite`, and one host `GetReg` (`/Users/david/Documents/Spatial Research/30 - HLS Mapping/70 - Lab1Part1 Tracer Bullet.md:35-51`).
3. Drive it from a dedicated test backend or Lab1-specific test hook that already has a compiled Spatial block. The backend can then run `g++` or `clang++` on the generated kernel-plus-oracle and expect success for `3`, `5`, and `8` (`/Users/david/Documents/Spatial Research/30 - HLS Mapping/70 - Lab1Part1 Tracer Bullet.md:103-123`).
4. Promote the pass to option A only after the Stage 0 extractor is stable. At that point, the production hook is a new `enableHLS` flag, CLI option, `HLSGen(state)` lazy val, and one conditional pass in the existing codegen section.

This path keeps the first proof close to the EE109 contract and away from legacy backend coupling. It also avoids giving HLS the wrong abstraction: CppGen's reusable idea is the ABI ordering, not its text or `FringeContext` launcher. A standalone generator can still borrow small policies, such as C integer spelling and simple arithmetic expression emission, without inheriting `TopHost.cpp`, `ArgAPI.hpp`, target Makefile copying, or suppressed accelerator emission.
